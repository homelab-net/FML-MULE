================================================================================
1. RED-TEAM RESULT
================================================================================

The proposed enhancement is technically compatible with the current FML/MULE
architecture, but several earlier formulations required correction before
implementation.

1.1 KEEP: DISTRIBUTED AWARENESS / OBSERVATION PLANE

The concept is compatible with the existing EUD/ESD capability direction:
- MULE-native observations;
- opportunistic EUD observations;
- specialist ESD observations;
- local-first processing;
- upstream-first TAK/Meshtastic/native integration;
- adaptive information fidelity;
- semantic AAR rather than packet archives.

The enhancement should be treated as a logical architecture and a family of
small decision functions/adapters, not automatically as a new daemon.

1.2 MODIFY: COMMON JSON IS A SEMANTIC CONTRACT, NOT A UNIVERSAL WIRE PROTOCOL

FML shall not force all mission data into proprietary JSON.

A small versioned machine-readable vocabulary is appropriate for:
- capability descriptors;
- capability records;
- task semantics;
- normalized observation semantics;
- test fixtures;
- local IPC/API boundaries where justified.

Actual mission data should continue to use appropriate existing representations:
- CoT for TAK/geospatial mission objects;
- MQTT where appropriate for machine-facing telemetry;
- HTTPS/REST for request-response services;
- RTSP/ONVIF/HTTPS where appropriate for cameras;
- Meshtastic-native supported payloads for degraded LoRa workflows;
- documented native radio/vendor protocols through protocol-specific adapters.

Illustrative JSON in this document defines semantics only. Do not freeze exact
field names or make it the mandatory mesh transport until evidence justifies it.

1.3 MODIFY: NO GENERIC "AWARENESS SERVICE" DAEMON YET

Do not create a new standalone awareness/fusion/tasking daemon merely to match a
diagram.

Follow AGENTS.md:
- exercise the end-to-end behavior first in test/digital_twin;
- keep hardware readers behind narrow fakeable interfaces;
- promote demonstrated runtime decisions into mule/ only when justified;
- reuse existing status, gateway, TAK, ingress, mission, and catalog boundaries
  where their responsibilities genuinely fit;
- create a new service only if a second-order need demonstrates that a process
  boundary is required.

The Status Aggregator remains node/status oriented. Do not turn it into a
mission-observation database by convenience.

1.4 MODIFY: EUD SENSING EXPANDS THE SECURITY/THREAT BOUNDARY

The current threat model explicitly places EUD internals outside its scope.
An FML EUD companion/ATAK plugin that performs Wi-Fi/BLE/GNSS/cellular sensing
changes that boundary.

Before a production EUD sensing implementation:
- update the threat-model scope;
- define permission/consent behavior;
- separate view, task, and administer authorization;
- document background-execution/mobile-OS constraints;
- preserve device-local policy so a MULE task cannot bypass EUD permissions;
- avoid persistent third-party identifier tracking by default.

The software contract and fake EUD may be implemented now.

1.5 MODIFY: EMCON-RX AND HARD-SILENT ARE PROPOSED SUB-PROFILES, NOT YET NEW
TOP-LEVEL CONTROLLED MODES

Current code recognizes the existing EMCON-SILENT emission axis. The proposed
distinction is useful:

NORMAL
EMCON-RX
HARD-SILENT

But production promotion of those labels may touch the controlled CONOPS
operating-mode semantics / CCR-01.

Therefore:
- simulate the behavioral distinction later, under test-local names;
- model it as proposed emission-policy subprofiles;
- do not silently alter the controlled operator-state vocabulary;
- mule/modes.py EmissionPosture is only NORMAL-EMISSION or EMCON-SILENT.
  CCR-01 is OPEN. EMCON-RX and HARD-SILENT are not modes;
- do not claim HARD-SILENT electromagnetic performance until measured with
  independent RF instrumentation;
- do not reuse mule/status.py Observations or NodeStatus.data_stale as the
  mission-observation store. Those are the operator view.

1.6 MODIFY: MULE GNSS/PNT CAPABILITY IS CONDITIONAL

Current architecture treats MULE GNSS as optional mission hardware for time
discipline; EUDs remain the normal source of participant PLI.

Therefore:
- MULE-native PNT integrity is a conditional capability when the hardware exposes
  appropriate data;
- no baseline MULE capability shall require GNSS merely to support the awareness
  architecture;
- time credibility remains the existing RTC/chrony/FML-ADR-042 path;
- do not claim spoofing detection from a commodity single-receiver GNSS path.

1.7 MODIFY: "RULES ENGINE" BECOMES SMALL DETERMINISTIC DERIVED ALERTS FIRST

Do not create a generalized policy/rules platform.

First implement narrow, testable evaluators such as:
- geofence/hazard entry;
- observation stale/expired;
- link-degradation trend;
- threshold-based weather/environment alert;
- capability unavailable/degraded.

Only extract a generalized rules abstraction after multiple real evaluators
demonstrate a common need.

1.8 MODIFY: "PARTITION PREDICTION" BECOMES A LINK-DEGRADATION TREND INDICATOR

Do not claim probabilistic prediction without evidence.

A useful software-only capability is:
- detect sustained decline in available link indicators;
- detect loss of path diversity / a single remaining IP path;
- tell the operator connectivity is degrading;
- state the available fallback bearer.

This is deterministic trend/status reporting, not AI forecasting.

1.9 KEEP: SECOND MILSIM / FIELD-EXERCISE SCENARIO

A second scenario adds value because it stresses different architecture:
- mobility;
- frequent topology change;
- EMCON;
- intermittent partitions;
- opportunistic EUD sensing;
- RF/communications-terrain mapping;
- tasking;
- disconnected collection;
- source-density changes.

It remains a secondary architecture stress scenario, not a replacement for the
wildfire/disaster-response integrated reference scenario.

1.10 KEEP: SOFTWARE CAN PROCEED NOW

The enhancement work can proceed while hardware is pending if claims remain
honest.

SIMULATED may cover:
- schema/semantic validation;
- task authorization and leases;
- observation lifecycle;
- deduplication/correlation logic;
- entity lifecycle;
- stale/TTL handling;
- store-and-forward behavior;
- representation/fidelity decisions;
- geofence/derived alerts;
- link-trend logic;
- deterministic SITREP generation;
- scenario behavior;
- CoT/MQTT/native adapter semantics against fakes/fixtures.

SIMULATED cannot establish:
- real Wi-Fi/BLE scan behavior;
- monitor-mode support;
- Remote ID reception on target hardware;
- SDR performance;
- RF range;
- RF terrain accuracy;
- HaLow/LoRa coexistence;
- electromagnetic silence;
- Android/iOS background behavior;
- battery impact;
- thermal impact;
- timing/latency under target load.


1.11 KEEP: OFFLINE-FIRST EUD ONBOARDING

CORE_READY shall be attainable with:
- no WAN;
- no Tailscale enrollment;
- no enhanced sensor permissions;
- no FML sensor plugin;
- only the local MULE, mission package, local trust/configuration, and supported
  TAK client behavior required for the baseline EUD role.

Enhanced sensing and remote continuity are OPTIONAL branches. Refusal, absence,
or temporary unavailability of either branch shall not cause baseline onboarding
to fail.

1.12 MODIFY: AP ASSOCIATION INFERS TEAM CONTEXT BUT DOES NOT GRANT AUTHORIZATION

Joining MULE-C's AP should make TEAM C the default enrollment context. This is a
usability rule, not an authorization primitive.

Do not allow possession of an AP credential alone to mint a durable mission or
remote-access identity. The mission's enrollment policy shall separately decide
whether the EUD may enroll.

1.13 ADD: TEAM-SCOPED REMOTE EUD CONTINUITY

Tailscale may be installed on approved EUDs as an OPTIONAL remote-continuity path.
The normal relationship is:

LOCAL:
EUD -> assigned MULE AP -> assigned MULE -> FML mesh/services

REMOTE, WHEN WAN EXISTS:
EUD -> Internet/WAN -> Tailscale -> assigned MULE mission ingress -> FML services

Remote EUD access shall remain anchored to the assigned MULE. An EUD assigned to
Team C shall not automatically fail over to Team A/B/D/E MULEs if MULE-C becomes
unreachable.

The preferred Tailscale authorization model is the one FML-ADR-082 now
decides. An admitted EUD carries one managed tag. That tag names the mission
and the assigned team. It does not name an operational role. One tag is the
whole infrastructure grant. The spelling is not frozen. An illustration, not
a schema, is:

  tag:eud-mission-<mission>-team-<team>
      -> assigned MULE approved remote-EUD ingress only

Do not compose that grant from several broad tags such as tag:eud +
tag:team-c. Tailscale tags are additive. A grant on any one of them widens
the endpoint. A MULE infrastructure tag does not name a mission or a team.
The ACL text that enforces the ingress is not decided. Signed mission policy
remains who the person is, what role they hold, and what they may see or do.

This is a deliberate exception, now recorded in FML-ADR-082, to Tailscale's
guidance that tags are for non-human devices. Ordinary operators do not hold
Tailscale user accounts. FML keeps the mapping between the person, the EUD,
and the tagged node. The tag is the overlay name of an assignment FML has
already authorized. It is not mission authorization.

Tailscale is not part of CORE_READY and shall never become a hidden prerequisite
for local mission execution.

1.14 ADD: REMOTE ENROLLMENT REQUIRES CONTROL-PLANE REACHABILITY

If WAN/Tailscale coordination is unavailable during onboarding:
- complete local mission onboarding;
- complete TAK configuration;
- complete optional local sensor setup if desired;
- record remote-continuity desired state as a waiting-for-WAN condition.
  PENDING_WAN is a proposed label only. FML-ADR-082 does not put that
  spelling in mule/status.py;
- do not fail the EUD's local mission readiness.

Do not solve this by stockpiling reusable Tailscale auth keys on field MULEs.
Where remote enrollment is authorized, prefer a narrowly scoped provisioning
path that obtains a one-use/pre-authorized credential only when control-plane
reachability exists.

External dependency facts verified 2026-09-23 against current Tailscale docs:
- OAuth clients with auth_keys scope can create tagged auth keys;
- one-off auth keys are supported;
- tags are additive identities, not an intersection of multiple tags;
- tagged devices lose user identity and are intended by Tailscale for non-human
  devices, making FML's tagged-EUD use an explicit architectural exception;
- if the Tailscale coordination server is unavailable, existing devices may keep
  working from cached state, but new users/devices cannot be added.

References:
https://tailscale.com/docs/features/oauth-clients
https://tailscale.com/docs/features/access-control/auth-keys
https://tailscale.com/docs/features/tags
https://tailscale.com/docs/reference/coordination-server-down

================================================================================
2. ENHANCED PRODUCT THESIS
================================================================================

Existing product thesis:

Configure a mission, enroll approved people/nodes/devices/capabilities, verify
readiness, preserve useful information as conditions degrade, protect higher-
value traffic, and reconstruct what happened afterward.

Enhancement:

Every MULE deployment should also be able to turn approved sensors already
present on MULEs, EUDs, and specialist ESDs into a distributed local-first
awareness fabric without requiring the operator to understand sensor transport,
routing, adapters, or bearer mechanics.

Conceptual flow:

MULE NATIVE       EUD OPPORTUNISTIC       SPECIALIST ESD
   |                     |                     |
   +---------------------+---------------------+
                         |
                    OBSERVATIONS
                         |
             validate / freshness / policy
                         |
            local correlation / aggregation
                         |
              useful mission representation
                         |
            +------------+------------+
            |            |            |
           TAK         Portal         AI
            |
           AAR

The MULE remains the mission-service/security gateway for EUD access. Optional
EUD Tailscale termination does not grant direct access around the assigned MULE;
remote EUD traffic still terminates at approved MULE mission ingress. Sensors do
not become privileged because they can publish data.

3. SENSOR SOURCE MODEL
================================================================================

A physical device may hold one or more existing roles:
CLIENT
SERVICE_HOST
EVENT_SOURCE
GATEWAY
INFRASTRUCTURE_NODE

Sensor behavior is expressed through capabilities, not hardware SKU.

3.1 MULE-NATIVE SOURCE

Conditional capabilities depending on fitted hardware/driver support may include:
- own node/network state;
- link observations;
- Wi-Fi environment;
- BLE environment;
- HaLow link/environment observations;
- LoRa link/environment observations;
- GNSS/PNT observations when fitted;
- local time/clock health;
- local power/thermal/status observations.

MULE-native sensing must not assume a receiver can be made passive/silent without
hardware evidence.

3.2 EUD SOURCE

EUD support has three valid capability levels. The first is baseline and the
others are optional enhancements.

3.2.1 BASELINE EUD — NO FML SENSOR SOFTWARE REQUIRED

A baseline EUD uses ATAK/iTAK and connects to its assigned MULE AP.

The MULE may obtain or correlate, where supported:
- normal TAK/CoT PLI and mission traffic;
- AP-side association state;
- AP-side link measurements such as signal/RSSI, rate, retries/failures, traffic,
  airtime, and other readings exposed by the selected Linux Wi-Fi stack/driver;
- team/mission context from the MULE through which the device enrolled.

A baseline EUD therefore remains useful for communications-terrain and link-health
work even when the user installs no FML sensor component and grants no enhanced
sensor permissions.

Do not claim that AP ownership grants the MULE access to the EUD's GNSS, BLE scan,
Wi-Fi scan, cellular radio metrics, camera, microphone, or motion sensors. Those
remain client/OS-controlled resources.

3.2.2 WEB-ENHANCED EUD — OPTIONAL

The MULE onboarding/dashboard web application may request browser-supported
permissions/capabilities where the platform exposes them, for example location,
motion/orientation, and operator-directed media capture.

Web-enhanced sensing is opportunistic:
- it shall not be required for CORE_READY;
- it shall not be treated as equivalent to a persistent native background agent;
- unsupported browser capabilities shall be reported as UNAVAILABLE rather than
  treated as an onboarding defect.

3.2.3 NATIVE/TAK-INTEGRATED EUD SENSOR — OPTIONAL

Android is the preferred full enhanced-EUD implementation path because an ATAK
plugin can interact with ATAK and Android capabilities while keeping ATAK as the
operator's normal UI.

When authorized and supported, the Android EUD sensor component may expose:
- position;
- Wi-Fi environment;
- BLE environment;
- Remote ID observations where supported;
- cellular-environment state where exposed by Android/device APIs;
- motion sensors;
- magnetometer/barometer where useful;
- operator-initiated imagery;
- bounded local buffering;
- bounded sensor task execution;
- capability/permission health.

The Android component should remain a thin sensor shim rather than a second
mission application. Fusion, correlation, mission policy, task authorization,
communications-terrain logic, and operator-level presentation remain MULE-side.

For iOS/iTAK, preserve the same capability contract but do not assume Android-style
plugin sideloading or feature parity. Current public iTAK material identifies an
SDK/plugin-development architecture, but the production distribution/install path
shall be verified before baselining an iOS implementation. A thin companion app
is an acceptable fallback if direct iTAK integration cannot satisfy the need.

References verified 2026-09-23:
https://tak.gov/pages/our-process
https://tak.gov/pages/sdks
https://tak.gov/solutions/law-enforcement
https://apps.apple.com/us/app/itak/id1561656396

3.2.4 PERMISSION MODEL

Sensor permissions are optional and individually evaluated.

Example:

EUD-C03
  CLIENT                    READY
  TAK                       READY
  MULE_LINK                 READY
  position.location         UNAVAILABLE   # permission denied
  rf.wifi_environment       READY
  rf.ble_environment        UNAVAILABLE   # permission denied

Permission denial shall:
- remove/degrade only the affected capability;
- never bypass the OS permission model;
- never fail baseline EUD enrollment;
- remain reversible if the user enables the permission later.

3.2.5 EUD READINESS MODEL

CORE_READY means baseline mission participation is functional.

Optional states are reported separately:
- ENHANCED_SENSORS_READY / PARTIAL / DISABLED / UNAVAILABLE;
- REMOTE_CONTINUITY_READY / PENDING_WAN / DISABLED / UNAVAILABLE.

Do not redefine READY to mean that all optional features were accepted.

4. RF SENSOR AS AN ESD
================================================================================

An RF sensor is a valid ESD.

Typical roles:
EVENT_SOURCE
and, when translating an external/native protocol,
GATEWAY

Example:

Device:
ESD-RF-03

Roles:
EVENT_SOURCE
GATEWAY

Capabilities:
rf.adsb
rf.spectrum_summary
rf.aprs

The RF sensor may be:
- an SDR plus managed host;
- a dedicated protocol receiver;
- another approved networked receiver;
- a future integrated receiver.

The rest of FML should consume the capability, not depend on the vendor/device

Do not baseline:
- communications-content interception;
- persistent third-party tracking;
- cellular identity collection;
- raw wideband IQ capture;
- precise emitter geolocation;
- generic direction finding.

Such functions are outside this enhancement unless separately authorized,
legally reviewed, and justified.

================================================================================
5. THREE INFORMATION OBJECTS
================================================================================

Keep three concepts separate.

5.1 OBSERVATION

Meaning:
A source reported or measured something at a time.

Observation is evidence, not truth.

Illustrative semantic envelope only:

{
  "schema": "fml.observation/0.x",
  "event_id": "fake-observation-id",
  "source": {
    "device_id": "FAKE-EUD-01",
    "capability": "rf.remote_id"
  },
  "observed_at": "2030-01-01T00:00:00Z",
  "received_at": "2030-01-01T00:00:01Z",
  "sensor_position": {
    "lat": 0.0,
    "lon": 0.0,
    "accuracy_m": 10
  },
  "observation_type": "uas.remote_id",
  "ttl_s": 15,
  "payload": {}
}

Required semantics should eventually answer:
- who produced it;
- capability/source type;
- when observed;
- when received;
- sensor position where available;
- measurement/object position where available;
- freshness/TTL;
- provenance/quality facts;
- typed payload;
- related task ID where applicable.

Do not create a universal numerical FML confidence score.

5.2 ENTITY / TRACK / AGGREGATE

Meaning:
A local correlation/fusion process concludes that multiple compatible
observations refer to one logical mission object or one aggregate condition.

Examples:
- multiple Remote ID observations -> one UAS entity;
- multiple ADS-B receptions -> one aircraft track;
- multiple link observations -> one communications-terrain cell/statistic;
- multiple environmental observations -> one area/threshold state.

Correlation shall be capability-specific.

Do not build a generic AI identity engine that tries to infer that an anonymous
Wi-Fi device, BLE device, camera detection, and person are the same individual.

5.3 OPERATOR PRODUCT

Meaning:
The representation appropriate to the user.

Examples:
- aircraft/UAS -> CoT/TAK track;
- hazard -> TAK point/area + alert;
- weather -> TAK object + portal telemetry;
- communications terrain -> map/grid overlay;
- camera -> snapshot/video/detection representation;
- capability health -> portal/readiness state.

Operator products should hide protocol/device mechanics unless diagnostics are
requested.

================================================================================
7. SENSOR TASKING
================================================================================

Tasking should ask for a capability outcome, not low-level implementation
details.

Supported conceptual task modes:

PERIODIC
Sensor samples/reports on a policy schedule.

EVENT
Sensor reports when a defined condition occurs.

TASKED
MULE or authorized user requests bounded collection.

CONTINUOUS
Long-running stream; requires explicit resource/policy handling.

Illustrative task semantics:

{
  "schema": "fml.task/0.x",
  "task_id": "fake-task-id",
  "capability": "rf.wifi_environment",
  "action": "survey",
  "duration_s": 8,
  "priority": "routine",
  "expires_at": "2030-01-01T00:01:00Z"
}

The common task contract should not expose arbitrary SDR gain/sample-rate/radio
internals. Sensor-specific adapters own those implementation details.

Task authorization shall distinguish:
VIEW

14. SECURITY / PRIVACY / RETENTION
================================================================================

Recommended data classes:

TRANSIENT
- raw local link/RF measurements;
- anonymous Wi-Fi/BLE environment observations;
- short-lived correlation evidence;
- short-lived enrollment transaction state.

OPERATIONAL
- active tracks;
- current hazards;
- current weather;
- current communications terrain;
- current sensor/capability state;
- current EUD readiness/assignment state.

MISSION HISTORY
- important alerts;
- selected tasked observations;
- operator reports;
- policy-approved products;
- relevant enrollment/reassignment events without retaining secrets.

AAR
- semantic state transitions/events selected by mission policy.

RAW CAPTURE
- off by default;
- not introduced by this enhancement merely because storage is available.

Preserve existing security principles:
- unique device identity;
- human identity separate from device identity;
- network admission != mission enrollment;
- mission enrollment != capability publication;
- capability publication != administration;
- AP association/team inference != authorization;
- no MAC address as primary identity;
- no credentials/unnecessary real location in logs;
- explicit freshness;
- fail closed on unauthorized capability publication or remote access.

For Wi-Fi/BLE awareness:
- aggregate where possible;
- avoid long-term raw third-party identifier retention;
- do not build persistent person/device tracking as a default feature.

14.1 EUD THREAT-BOUNDARY EXPANSION

Production enhanced-EUD sensing expands the current threat boundary because the
FML system begins relying on client-side permissions, native APIs, and optional
background execution.

Before production promotion:
- update THREAT_MODEL.md;
- define permission and consent behavior;
- separate VIEW/TASK/ADMINISTER authorization;
- preserve device-local permission enforcement;
- document Android/iOS background limitations;
- treat unavailable/revoked permissions as capability loss, not authorization to
  bypass the OS.

14.2 LOCAL EUD ENROLLMENT SECURITY

Joining a MULE AP establishes context, not authorization.

A leaked Wi-Fi/AP credential shall not be sufficient to mint a durable FML mission
identity or remote-access identity. Enrollment policy shall be separately enforced.

Mission configuration may support controlled enrollment windows, expected device
counts, administrator approval, one-time onboarding tokens, or another simple
mechanism consistent with the controlling identity architecture. Do not add user
friction without a demonstrated security need, but do not collapse AP admission
and mission enrollment into the same trust decision.

14.3 TAILSCALE REMOTE-CONTINUITY SECURITY

The remote EUD path is an OPTIONAL extension of the mission boundary.

Preferred policy characteristics:
- EUD remote identity is scoped to mission + team;
- EUD can reach only its assigned MULE's approved mission-ingress services;
- no EUD-to-EUD Tailscale access by default;
- no EUD-to-other-team-MULE access by default;
- no SSH/database/management-plane access from an EUD tag;
- no EUD subnet-router or exit-node role;
- no broad reusable enrollment secret stored on field MULEs;
- FML retains the human <-> EUD <-> Tailscale-node audit mapping.

Tailscale tags are additive identities. FML-ADR-082 selects one tag on the
admitted EUD. An illustration, not a frozen spelling:

  tag:eud-mission-<mission>-team-<team>

That tag names the mission and the assigned team and does not name a role.
Do not rely on the intersection of broad tags such as:

  tag:eud + tag:mission-alpha + tag:team-c

because a grant applying to any one tag can widen access. A MULE
infrastructure tag does not name a mission or a team. The ACL text is not
decided.

14.4 REMOTE PROVISIONING AUTHORITY

The shape below is a preferred direction. It is not the grant syntax
FML-ADR-082 decided. That syntax is still open. Do not stockpile reusable
keys, and do not treat this sketch as an implemented control.

MULE-C
  -> authenticated request for one Team-C EUD enrollment
  -> narrow FML provisioning authority
  -> Tailscale API/OAuth
  -> one-use/pre-authorized mission+team-scoped credential
  -> EUD enrollment

A prototype may use a narrower per-MULE credential only if it is technically
constrained to the intended child tag and cannot administer unrelated tailnet
resources. Centralization of the higher-value OAuth secret is preferred.

If WAN/control-plane reachability is absent, store only desired state and retry
when allowed; do not cache pools of reusable auth keys to simulate offline Tailscale
enrollment.

14.5 TEAM REASSIGNMENT

Changing the assigned MULE/team is an explicit administrative event.

Example:
EUD-C03 -> ADMIN REASSIGN -> Team D

Required behavior:
- local mission assignment changes under admin authorization;
- old remote identity/access is revoked/replaced when control-plane reachability
  allows;
- new mission+team-scoped remote identity is provisioned if remote continuity is
  enabled;
- the device shall not silently accumulate Team-C and Team-D remote authorization.

18. IMPLEMENTATION LOCATION RULES
================================================================================

Do not start by creating production modules for everything.

Preferred progression:

STEP 1
test/digital_twin fixtures/fakes/scenarios demonstrate semantics.

STEP 2
tests prove the decision must exist and can fail.

STEP 3
pure runtime decision logic that has earned promotion may move to mule/ under
FML-ADR-051 / FML-ADR-052 discipline.

STEP 4
hardware/mobile/native readers remain behind narrow interfaces and replace
fakes later.

STEP 5
process/service boundaries are created only when demonstrated behavior requires
a distinct runtime service and the relevant gate permits it.

Candidate pure decisions eventually suitable for mule/ after evidence:
- freshness/lifecycle assessment;
- task authorization/lease decision;
- deterministic correlation for keyed observations;
- geofence evaluation;
- link-degradation trend;
- communications-terrain aggregation policy;
- representation selection;
- deterministic SITREP reduction.

Do not move RF/OS readers into production merely because a parser exists.

19. RED-TEAM FAILURE CASES TO ADD
================================================================================

Add deterministic tests for:

DUPLICATE OBSERVATION
Same event arrives through multiple sources.
Expected: one entity where capability-specific correlation proves sameness.

FALSE MERGE
Two different keyed objects are close in space/time.
Expected: remain distinct.

STALE REJOIN
Partitioned source reconnects with expired observation.
Expected: history/AAR only, not live COP.

CLOCK PROBLEM
Observation time credibility is degraded.
Expected: freshness/authority handling does not pretend precise current state.

TASK AFTER EXPIRY
Late task arrives after expires_at.
Expected: refuse.

UNAUTHORIZED TASK
Viewer attempts TASK action.
Expected: refuse.

ORPHAN CONTINUOUS TASK
Controller disappears.
Expected: lease expires and stream/task stops.

CHATTY SENSOR
Rate exceeds policy.
Expected: rate limit without starving critical traffic.

CAPABILITY DRIFT
ESD descriptor changes after update.
Expected: revalidate before widening published capability.

EUD PERMISSION DENIED
User refuses one or all enhanced sensor permissions.
Expected: CORE_READY succeeds; only affected sensor capabilities become
DISABLED/UNAVAILABLE.

EUD PERMISSION REVOKED
Previously available permission is revoked.
Expected: capability becomes unavailable/degraded; MULE does not bypass.

EUD SENSOR COMPONENT ABSENT
ATAK/iTAK is present but optional FML sensor integration is absent.
Expected: baseline CLIENT role and AP-side link observations still function.

TAILSCALE DECLINED
User chooses not to enable remote continuity.
Expected: CORE_READY and local mesh/service access remain successful.

NO WAN DURING ONBOARDING
Mission profile and MULE are available but no Internet/control-plane reachability
exists.
Expected: local EUD onboarding, TAK setup, local service access, and optional local
sensor setup complete; remote continuity is DISABLED or PENDING_WAN.

PENDING REMOTE ENROLLMENT
User requested remote continuity with no WAN, then WAN becomes available.
Expected: a fresh authorized provisioning transaction completes; no reusable
stockpiled key is required.

AP CREDENTIAL LEAK / UNAUTHORIZED ENROLLMENT
Unknown EUD joins MULE-C AP but mission enrollment policy does not authorize it.
Expected: Team-C context may be inferred, but durable mission/remote identity is
not issued.

WRONG-TEAM REMOTE ACCESS
A Team-C tagged EUD attempts to reach MULE-B.
Expected: denied.

EUD-TO-EUD REMOTE ACCESS
EUD-C1 attempts to reach EUD-C2 over the tailnet without an explicit requirement.
Expected: denied.

REMOTE MANAGEMENT ACCESS
Tagged EUD attempts SSH/database/admin access on assigned MULE.
Expected: denied unless a separately approved role explicitly allows it.

ASSIGNED-MULE REMOTE FAILURE
Remote Team-C EUD has WAN; MULE-C loses Tailscale/WAN reachability.
Expected: Team-C EUD loses remote FML access; it does not silently fail over to
MULE-A/B/D/E.

ASSIGNED-MULE MESH FAILURE
Remote Team-C EUD reaches MULE-C over Tailscale but MULE-C loses field mesh.
Expected: EUD retains only services/state locally available from MULE-C; system
reports degraded mesh reachability accurately.

LOCAL PATH PRESENT
EUD is physically on assigned MULE AP while Tailscale is also available.
Expected: local path is preferred; traffic is not intentionally hairpinned through
WAN to the same MULE.

TEAM REASSIGNMENT
EUD moves administratively from Team C to Team D.
Expected: local assignment changes explicitly; old remote access is revoked/replaced
when control-plane reachability allows; EUD does not accumulate both team grants.

ADDITIVE TAG POLICY ERROR
Test fixture intentionally adds a broad tag/grant that would widen EUD access.
Expected: policy validation/lint catches or test suite demonstrates the unintended
reachability before deployment.

EMCON TASK ATTEMPT
Remote survey requested while policy prohibits transmission/tasking.
Expected: refuse/defer according to policy.

STALE COMMS TERRAIN
Old samples dominate a cell.
Expected: freshness weighting/expiration prevents old terrain from appearing
current.

MOVING-ENDPOINT MISINTERPRETATION
RSSI changes while both endpoints move.
Expected: store endpoint/time context; no fixed-site/emitter-location conclusion.

OPTIONAL GNSS ABSENT
MULE has no GNSS.
Expected: baseline awareness still functions; PNT-specific capability absent.

UNKNOWN HARDWARE READER
Platform cannot expose a reading.
Expected: None/UNKNOWN, not healthy/zero.

21. DEFINITION OF SUCCESS — SOFTWARE PHASE
================================================================================

Against fakes/fixtures, the software enhancement should demonstrate:

- MULE, EUD, and ESD sources can enter one semantic observation path;
- capability declaration is distinct from authorization and validation;
- RF-awareness ESD behaves as an ordinary capability-bearing ESD;
- task authorization distinguishes VIEW/TASK/ADMINISTER;
- bounded tasks expire;
- task results become observations;
- observations preserve source/time/freshness/provenance;
- duplicate keyed observations correlate without duplicate COP objects;
- false merges are rejected;
- entity lifecycle reaches stale/expired correctly;
- expired reconnect data cannot masquerade as current;
- communications terrain accepts moving endpoints;
- communications terrain exposes evidence/freshness rather than a misleading
  RSSI-only heatmap;
- optional GNSS absence does not break baseline awareness;
- deterministic derived alerts work;
- disconnected queue/rejoin works;
- deterministic SITREP works without AI;
- representation adapts to link/budget constraints;
- LoRa path receives compact selected events, not arbitrary JSON tunneling;
- proposed EMCON policies change collection/distribution behavior in simulation;
- Scenario A exercises broad integration;
- Scenario B exercises mobility/EMCON/partition stress;
- AAR records semantic events sufficient to explain fusion/tasking/degradation;
- a mission profile can assign multiple MULEs to teams and activate locally with no
  WAN dependency;
- an EUD can reach CORE_READY through its assigned MULE with no WAN, no Tailscale,
  no sensor plugin, and all enhanced sensor permissions denied;
- AP/MULE context defaults the team without making AP association the sole
  enrollment authorization decision;
- baseline EUD AP-side link observations remain available without enhanced client
  sensing;
- enhanced sensor permission denial removes only affected capabilities;
- remote continuity can be skipped without affecting local readiness;
- remote continuity can remain PENDING_WAN without affecting local readiness;
- simulated remote EUD access is scoped to the assigned MULE and approved ingress;
- simulated assigned-MULE failure does not cause cross-team remote failover;
- team reassignment does not accumulate stale remote authorization;
- no reusable real Tailscale auth key exists in source, fixture, evidence, or
  mission package;
- all claims remain SIMULATED unless real hardware/mobile/client evidence exists.

22. HARDWARE VALIDATION HANDOFF
================================================================================

When hardware arrives, do not redesign this architecture first.

Replace fakes one interface at a time and determine which assumptions fail.

Priority physical/mobile validation:
1. target-radio enumeration/readers;
2. AP-side EUD link telemetry on selected Wi-Fi hardware/driver;
3. Wi-Fi/BLE scan/receive behavior and AP/scanner concurrency;
4. representative Android/ATAK plugin install, permission, background, buffering,
   and task behavior;
5. representative iOS/iTAK integration/distribution path and supported sensor
   capability subset;
6. MULE-hosted onboarding flow on representative Android/iOS browsers;
7. Tailscale client enrollment UX on representative Android/iOS devices, including
   exact user-confirmation steps and PENDING_WAN recovery;
8. local-path preference when local Wi-Fi and Tailscale are simultaneously present;
9. HaLow/LoRa coexistence and scan/transmit controls;
10. receive-dominant/EMCON behavior;
11. independent measurement of claimed transmit suppression;
12. GNSS fields actually exposed by candidate receiver;
13. RF sensor/SDR performance where fitted;
14. power/thermal impact of sensing;
15. real communications-terrain measurements versus synthetic logic.

A hardware finding may:
- confirm the fake boundary;
- change the reader/interface;
- narrow a capability;
- remove a capability;
- create a new trade;
- require controlled CONOPS/ADR change.

Do not preserve the software design merely because it already exists.

23. SCOPE GUARDRAILS
================================================================================

Do not use this enhancement to justify:
- a custom TAK replacement;
- a custom LoRa PHY/protocol;
- a custom MANET protocol;
- Kubernetes or distributed application scheduling;
- a fleet-wide distributed observation database;
- a generic AI fusion engine;
- autonomous AI network control;
- a plugin marketplace;
- persistent anonymous device/person tracking;
- broad communications interception;
- arbitrary IQ collection as a default;
- precise emitter geolocation from ordinary RSSI;
- a new daemon for every logical box in a diagram.
- WAN/Tailscale as a prerequisite for baseline mission execution;
- silent OS permission grants or attempts to bypass mobile permission controls;
- AP association as the sole durable mission-enrollment authorization;
- broad EUD access to the entire tailnet;
- automatic cross-team MULE failover for remote EUDs;
- reusable pools of Tailscale auth keys stored on field MULEs;
- treating optional sensor/Tailscale refusal as an onboarding failure.

Prefer:
- deterministic policy;
- upstream/native representations;
- local-first processing;
- bounded queues;
- freshness/TTL;
- evidence counts;
- explainable correlation;
- explicit unknown/unavailable state;
- small reusable primitives;
- tests that fail without the behavior;
- SIMULATED now, physical evidence later.

25. GUIDING ENHANCEMENT RULE
================================================================================

MULE should convert approved sensing that is already present on MULEs, EUDs, and
specialist ESDs into useful mission awareness without forcing operators to
understand sensor transport, routing, protocol adapters, or bearer mechanics.

The system should preserve the distinction between:
- what a sensor observed;
- what FML can defensibly correlate or derive;
- what the operator is shown.

It should preserve provenance and freshness, degrade representation before
dropping useful information, collect locally through partitions where policy
permits, and never turn software simulation into a claim about physical RF
behavior.

For EUDs, the product rule is:

INSTALL ATAK/iTAK
-> JOIN THE ASSIGNED MULE AP
-> COMPLETE THE MULE WEB ONBOARDING FLOW
-> RETURN TO TAK
-> OPERATE

Sensor enhancement and remote continuity may improve that experience, but neither
is permitted to become a prerequisite for baseline local mission participation.
A five-MULE mission shall still be provisionable, form its local network, onboard
EUDs, and execute authorized mesh-carried mission services with no WAN.
