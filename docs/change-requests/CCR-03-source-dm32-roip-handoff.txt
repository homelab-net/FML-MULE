===============================================================================
1. PURPOSE
===============================================================================

This handoff defines the architectural change required to integrate the
group-standard BAOFENG DM-32UV into MULE as a native voice/RF bearer while
preserving the existing MULE local-first, multi-bearer, field-replaceable
architecture.

Primary operational concept:

    DM-32UV = familiar local RF voice interface
    EUD/ATAK = familiar digital situational-awareness interface
    MULE = bearer abstraction, routing/security boundary, gateway, and
           optional voice-extension transport

Desired user experience:

    Power on.
    Select assigned radio channel.
    Connect EUD to MULE.
    Use ATAK on the EUD.
    Use the DM-32UV + normal PTT/headset for voice.
    The user should not need to know whether linked voice traverses:
      - direct RF;
      - local MULE Wi-Fi;
      - HaLow;
      - Ethernet;
      - another MULE acting as WAN gateway;
      - Tailscale/WAN.

The goal is NOT to replace the handheld-radio workflow with VoIP.

The goal is to preserve the familiar handheld-radio interface while allowing
MULE to extend that voice traffic over available IP paths.

===============================================================================

Current CONOPS already supports the broader direction:

A. Local WAN Gateway
   Any standard MULE is technically capable of an authorized WAN-gateway role.

B. WAN Overlay
   Tailscale or another approved secure overlay may connect geographically
   separated MULEs.
   EUDs do not join the overlay directly.
   MULE remains the WAN routing/security boundary.
   Network reachability alone does not grant service authorization.

C. External VHF/UHF/HF Integration
   Current Section 45 already reserves:
   - Bluetooth;
   - Wi-Fi;
   - USB;
   - audio;
   - packet;
   - data;
   radio integration boundaries.

   45.1 EUD-connected radio
   45.2 RF gateway
   45.3 IP-enabled radio

D. Existing limitation
   Current Section 45 says vendor-specific CAT control, remote PTT,
   audio bridging, and broad commercial-radio automation remain downstream
   or stretch capabilities.

E. Existing future-feature bookmark

   - team-local PTT/voice;
   - meshed MULE TL-to-TL voice;
   - WAN-extended VoIP;
   - QoS/codec/signaling/bearer adaptation work.

This change matures that bookmark into an explicit integrated-RF architecture.

4. PROPOSED ARCHITECTURE DECISIONS
===============================================================================

FML-ADR-051
TITLE:
Group-standard external voice radio

DECISION:
BAOFENG DM-32UV is the selected initial group-standard external handheld
voice-radio candidate for the current FML hardware block.

RATIONALE:
- already baselined by the user group;
- common/familiar end-user interface;
- supports analog and DMR operation;
- inexpensive COTS replacement;
- avoids retraining users on a software-only PTT application;
- preserves independent radio PACE when MULE/EUD/WAN fails.

BOUNDARY:
The DM-32UV is not required for core MULE IP networking/TAK operation.
A future radio may replace it if the controlled radio-interface contract is met.

-------------------------------------------------------------------------------

FML-ADR-052
TITLE:
Audio/PTT-level Radio-over-IP baseline

DECISION:
MULE will extend handheld-radio voice using AUDIO + PTT state over IP.

Native DMR protocol tunneling/MMDVM is NOT required for the baseline.

RATIONALE:
- simpler;
- radio-agnostic;
- supports analog or DMR audio coming from the gateway radio;
- allows local and remote gateways to use different RF frequencies;
- retains ordinary user PTT behavior;
- avoids making one digital-radio protocol the architectural core.

-------------------------------------------------------------------------------

FML-ADR-053
TITLE:
Integrated MULE RF gateway

DECISION:
The preferred field architecture is an integrated dedicated gateway-radio
function inside or mechanically retained as part of each RoIP-capable MULE.

Prototype implementation may use:
- one BAOFENG DM-32UV;
- one DigiRig Mobile-class USB audio/PTT interface;
- one short K1/Kenwood-style audio/PTT cable;
- one controlled radio antenna feed.

Production cost-down may later replace the external DigiRig with equivalent
integrated USB-audio/PTT electronics after electrical qualification.

-------------------------------------------------------------------------------

FML-ADR-054
TITLE:
Operator headset path remains radio-primary

DECISION:
The user's normal headset/PTT path shall remain:

    ear protection/headset
        ->
    normal PTT
        ->
    personal DM-32UV

MULE audio is NOT directly mixed into the user's single-lead headset in the v1
baseline.

RATIONALE:
- prevents duplicate/echoed voice;
- preserves familiar user interaction;
- prevents MULE from becoming a dependency for ordinary local RF;
- avoids adding a dual-input audio mixer to every user;
- keeps complexity inside the team gateway, not on every operator.

Remote MULE-carried voice should reach the user by being retransmitted through
the local MULE gateway radio onto the local RF channel, then heard normally
through the user's DM-32UV/headset.

===============================================================================
6. FREQUENCY / CHANNEL BEHAVIOR
===============================================================================

Local radios must match their LOCAL gateway radio.

Remote sites do NOT need matching RF frequencies.

Example:

    Site Alpha local RF: Channel A
    Site Bravo local RF: Channel B

MULE transports:

    decoded audio
    +
    PTT/control state

over IP.

It does NOT transport or repeat the RF waveform itself.

Therefore:

    Channel A -> MULE IP -> Channel B

is valid if both local gateway configurations are authorized and correctly
configured.

The architecture must not hard-code actual RF frequencies into the software
baseline. Frequency/talkgroup/channel plans belong in mission configuration and
radio codeplug artifacts.

===============================================================================
7. AUDIO TOPOLOGY / DOUBLE-AUDIO RULE
===============================================================================

DO NOT baseline simultaneous delivery of the same linked voice through:
1. direct MULE-to-headset audio; AND
2. local gateway-radio retransmission.

That creates duplicate/echoed voice.

BAD:

    Remote voice
       |
      MULE
       |--------------------> user's headset direct
       |
       +--> local gateway radio -> user's DM-32 -> same headset

GOOD:

    Remote voice
       |
      MULE
       |
    local gateway radio
       |
      RF
       |
    user's DM-32
       |
    user's normal PTT/headset audio path

Result:
The operator hears one copy through the familiar radio interface.

Future direct MULE-to-headset audio MAY be considered for non-radio content
such as:
- AI assistant responses;
- ATAK alerts;
- navigation;
- private IP audio.

That requires a separate audio-mixing/dual-comm design and is not part of the
v1 integrated-RF baseline.

- active voice/PTT;

10. SOFTWARE ARCHITECTURE
===============================================================================

The coding agent shall acknowledge that integrated RF adds a new actual software
service, not merely a BOM item.

Required software functions:

1. USB AUDIO
   - ALSA capture from gateway radio
   - ALSA playback to gateway radio

2. PTT CONTROL
   - assert transmit
   - release transmit
   - maximum TX timeout
   - fail-safe unkey on process crash

3. RX ACTIVITY DETECTION
   TBR:
   - hardware COS/COR if available; OR
   - validated squelch/audio detection.

   Do not assume VOX/audio-energy detection is adequate until tested.

4. AUDIO CODEC
   Preferred starting point:
   Opus mono voice.

5. TRANSPORT
   - local peer IP;
   - HaLow/Wi-Fi;
   - Tailscale;
   - no cloud dependency for local operation.

6. SIGNALING
   At minimum:
   - origin node;
   - session ID;
   - voice group;
   - PTT start;
   - PTT stop;
   - destination;
   - authorization result;
   - timeout;
   - loop metadata.

7. AUTHORIZATION
   Distinct from network reachability.
   Tailscale peer != automatic radio keying permission.

8. LOOP CONTROL
   A remote stream shall not be re-ingested as a new local transmission and
   sent back indefinitely.

9. HALF-DUPLEX ARBITRATION
   Initial baseline may support one talker per voice group.

10. QoS
    Active voice should beat:
    - video;
    - bulk file transfer;
    - background sync.

11. STATUS
    Expose:
    - gateway radio present;
    - audio device healthy;
    - PTT state;
    - linked peers;
    - local/mesh/WAN state;
    - packet loss;
    - jitter;
    - last fault;
    - gateway enabled/disabled.

12. LOGGING
    Log metadata, not raw voice by default:
    - session start/stop;
    - source/destination node;
    - group;
    - path;
    - errors;
    - PTT timeout;
    - loop suppression.

13. CONFIGURATION
    Version-control:
    - radio codeplug;
    - channel plan;
    - voice-group map;
    - mission profile;
    - gateway enablement;
    - routing policy.

12. NETWORKING PATH / POLICY
===============================================================================

Voice should be treated as an application carried by the existing MULE IP
fabric.

Path priority is route-quality/policy dependent, not necessarily hard-coded by
radio type.

Potential paths:
- direct MULE peer IP;
- conventional Wi-Fi;
- HaLow;
- Ethernet;
- authorized WAN-gateway route;
- Tailscale.

LoRa/Meshtastic:
NOT a baseline voice bearer.

Voice-group routing:
Must be mission scoped.

Example logical services:
    voice.team-local
    voice.tl
    voice.command

Names are examples only.

MULE SHOULD prefer direct/local IP reachability over unnecessary WAN hairpinning
when both endpoints are locally reachable.

14. HEADSET / PTT USER-INTERFACE RULE
===============================================================================

For normal users:

    ear protection/headset
        |
    existing PTT
        |
    personal DM-32UV

MULE SHALL NOT be placed inline between the normal user's PTT and radio in the
v1 baseline.

MULE SHALL NOT simultaneously inject the same linked radio audio directly into
the user's single-lead headset while also retransmitting it over RF.

Reason:
double/echoed voice.

The integrated gateway radio is the bridge.

This preserves:
- normal radio ergonomics;
- normal radio failure behavior;
- direct RF fallback;
- simple volunteer training.

19. ACCEPTANCE INTENT
===============================================================================

The target end state is:

USER:
- familiar DM-32UV;
- familiar PTT;
- familiar ear protection/headset;
- familiar ATAK EUD.

MULE:
- integrated RF gateway;
- conventional Wi-Fi;
- HaLow;
- LoRa;
- Ethernet;
- USB-C power/data/WAN;
- Tailscale;
- TAK/field services;
- bearer-aware linked voice.

When everything works:
voice can be extended transparently.

When WAN fails:
local MULE-linked paths may remain.

When MULE fails:
ordinary direct RF remains.

When the EUD fails:
ordinary RF remains.

The technology should increase range and interoperability without making the
volunteer operator learn a new voice interface or making local voice depend on
the digital system.
