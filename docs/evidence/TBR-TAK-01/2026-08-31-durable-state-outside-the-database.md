# Durable state that is not in the database

**Trade:** `TBR-TAK-01`.
**Date:** 2026-08-31.
**Taken by:** Cameron Zobrist, on the lab development machine.
**Status of this artifact:** `UNVERIFIED`. Read from the source of
`OpenTAKServer` 1.7.13 as installed. **The server was still not run**, and the
boundary that puts on these findings is stated at the end.

## What this supplies

Outstanding item 2 of the six the 2026-08-27 analysis listed:

> **Locate every durable-set member.** Specifically whether any is stored
> outside the SQL backend. Finding 5, and the condition on `FML-ADR-034`.

**The answer is yes, in three places, and a database high-availability
mechanism protects none of them.**

## Where state lives

| Location | Default | What it holds |
| --- | --- | --- |
| SQL backend | `postgresql+psycopg://ots@127.0.0.1/ots` | The 36 tables classified in `2026-08-31-relational-state-decomposed-into-conops-classes.md` |
| `config.yml` | `$OTS_DATA_FOLDER/config.yml` | Node identity and every generated secret. See below. |
| `ca/` | `$OTS_DATA_FOLDER/ca` | The certificate authority |
| `uploads/` | `$OTS_DATA_FOLDER/uploads` | Uploaded files, created at import if absent |

`OTS_DATA_FOLDER` defaults to `~/ots`.

**The default backend is PostgreSQL, not SQLite.** `FML-ADR-034` and
`TBR-COMP-01` both assume something about the database; this records which one
upstream ships by default.

## `config.yml` is a durable-set member and does not look like one

On first run `opentakserver/app.py` writes **every** `DefaultConfig` attribute,
excepting only the language list, into `config.yml`. On later runs it loads that
file. So four values that `defaultconfig.py` generates at import are generated
**once** and then persist:

| Key | Generated by | Consequence if `config.yml` is lost |
| --- | --- | --- |
| `SECURITY_PASSWORD_SALT` | `secrets.SystemRandom().getrandbits(128)` | **Every stored password hash becomes unverifiable.** |
| `SECRET_KEY` | `secrets.token_hex()` | Sessions and signed tokens are invalidated. |
| `OTS_NODE_ID` | 32 random characters | The server presents a different node identity. |
| `OTS_MEDIAMTX_TOKEN` | `secrets.token_urlsafe` | The video path loses its shared token. |

**The password salt is the sharp one.** It is not reconstructable from anything,
it is not in the database, and losing it does not degrade authentication -- it
ends it. A restore that brought back a perfect copy of the database and not this
file would produce a server holding every user's hash and unable to verify any
of them.

That is squarely CONOPS 26.1: state that must be consistent across all eligible
service hosts. It is stored in a YAML file that a database replication mechanism
has no knowledge of.

## The certificate authority is a directory

`OTS_CA_FOLDER` defaults to `$OTS_DATA_FOLDER/ca`.

The `certificates` table was classified 26.1 in the decomposition, and that
stands, but **the table records issued certificates while the authority that
issues them is a folder.** A replacement host restored from a database backup
inherits the record of every certificate and no ability to issue or re-issue
one.

This is the concrete form of Finding 5 in the 2026-08-27 analysis --
"database high availability alone cannot protect the durable set" -- which was
reasoning then and is specific now.

## Two upstream defaults worth recording

Both are published upstream defaults rather than anything discovered, and
neither is a secret. They are recorded because a MULE image that ships them
unchanged ships them into the field.

- **`OTS_CA_PASSWORD` defaults to `atakatak`.** The certificate authority's key
  material is protected by a well-known constant.
- **`OTS_RABBITMQ_PASSWORD` defaults to `guest`**, with `OTS_RABBITMQ_USERNAME`
  `guest`.

`THREAT_MODEL.md` makes physical capture an expected condition. A captured node
whose CA is protected by a published default is a captured certificate
authority.

## An input to outstanding item 3

`OTS_RABBITMQ_TTL` is `86400000`, which is **24 hours in milliseconds**. So
messages in the broker have a bounded lifetime rather than being retained
indefinitely.

That is an input to item 3, "inspect durable queues for sole-copy
mission-critical items", and not an answer to it: a 24-hour TTL bounds how long
a sole copy could sit in a queue, and says nothing about whether one ever does.

## What this changes

`FML-ADR-034`'s condition can now be stated precisely rather than assumed. A
database-level continuity mechanism, of any kind, leaves three things
unprotected: the password salt and node identity in `config.yml`, the
certificate authority in `ca/`, and uploaded files in `uploads/`.

The 2026-08-27 analysis anticipated exactly this and left it as an open question
for `TBR-HA-01`: "whether a second, filesystem-shaped continuity mechanism is
required, or whether the program accepts unprotected state and tells the
operator". **That question is now answerable and the answer is that a
filesystem-shaped mechanism is required**, unless the program accepts that a
failover cannot authenticate users.
