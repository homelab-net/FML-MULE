# Documentation

This directory is the program's design record. It is the largest and most
important part of the repository, because at this stage the design is what the
program has.

## Reading order

If you are new, read in this order. Each stage assumes the one before it.

1. `conops/` - what the system is for and how it is meant to be used. **CONOPS
   v1.01, baselined**, transcribed verbatim. Every requirement traces back here.
2. `architecture/` - how the system is arranged to meet that concept. **SAD
   v0.31, drafted**, transcribed verbatim. The source of rationale for the ADR
   register.
3. `adr/` - the decisions taken, each with a stable `FML-ADR-###` identifier,
   its status, its consequences and its accepted cost.
4. `trades/` - the questions still open, each with a `TBR-<AREA>-##`
   identifier, an owner, and a closure gate.
5. `NON-GOALS.md` - what the program deliberately does not do. Read this before
   proposing anything; it will save you time.

If you are here to build something rather than to understand the design, read
`ROADMAP-DEV.md` after step 5. It sequences the work, says what each item is
blocked by, and points back into the documents above for the context each one
needs.

`STATUS.md` at the repository root carries the generated current view of
decisions, trades, the critical path, and vacant maintainer roles. It is
generated by `tools/gen-status.sh` and is never hand-edited.

## Document control

The CONOPS and the SAD are **controlling documents**, transcribed verbatim and
**not reformatted to this repository's house style**. Reformatting a document
under its own change control would alter a baselined artifact and put drift
between this copy and the one the signatories approved. markdownlint excludes
both deliberately, with the reason recorded in its configuration.

Do not edit either in place. A new version is issued and the file is replaced.

Changes go through the process in `change-requests/README.md`. CONOPS section 86
governs the CONOPS; the SAD is a controlled draft whose changes are ordinary
pull requests, except that altering a `SELECTED` decision still requires a
superseding ADR.

### Transcription integrity

Both documents carry their own audit figures, which gives five checks on these
copies. All five pass; see `conops/README.md` and `architecture/README.md`. The
second-reviewer confirmation required by SAD section 35.4 has **not** been
performed.

## Writing conventions

These are binding. See `CONTRIBUTING.md` for the full set.

- **Modal verbs are load-bearing.** `shall` is binding and verifiable, `should`
  is preferred and waiverable with recorded rationale, `may` is permitted and
  creates no obligation. Do not use `will` or `must` in a requirement.
- **Sentence case for headings. No emoji anywhere.**
- **Unknowns are `TBD` with a trade reference.** Never a plausible-looking
  number.
- **Unknown status is `UNVERIFIED`.** Never "tested", "verified" or "working".
- **Every claim about component behaviour cites a datasheet or a measurement**,
  archived under `evidence/`.

## Finding your way between a decision and the code

Three indexes, all generated, none hand-maintained:

| Question | Where to look |
| --- | --- |
| What is settled, what is open, who owns it? | `STATUS.md` |
| Which requirement is allocated where, and what validates it? | `docs/verification/traceability.md` |
| What implements this decision, and who explains it? | `docs/decision-index.md` |

`decision-index.md` is derived from the `FML-ADR-###` and `TBR-XXX-##`
citations in the tree, so it cannot drift: nobody writes it. It separates code
that **acts** on a decision from prose that **describes** one, because those are
different claims. An empty implementation column is not a defect at this stage;
most decisions here are deliberately not built yet, and the index exists so that
"decided and built" and "decided, not yet built" stay apart.

Going the other way, from code to reasoning, is the citation itself: every
module names the decision it serves, and `tools/validate-docs.sh` fails if a
cited identifier does not resolve.

## Requirement frontmatter

Requirement-bearing documents carry structured frontmatter so that traceability
is generated rather than hand-extracted. Hand-extracted traceability has
already failed once in this program's history; `tools/gen-traceability.sh`
exists so it does not fail again at a larger scale.

```yaml
---
requirements:
  - id: FML-REQ-001
    source: CONOPS 3.2
    modal: shall
    text: The node shall retain local time across power loss.
    allocation: FML-ADR-042
    stage: STAGE-2
---
```

A binding requirement (`modal: shall`) with no `allocation` or no `stage` is a
**defect**, and the CI check fails the build for it. A requirement no test
validates is a requirement nobody can be wrong about.

The requirement set is populated: `verification/requirements.md` carries the 33
CONOPS section 79 criteria with their section 85 stage mapping, and the check
reports zero defects. The 140-clause decomposition in SAD section 35.2 belongs
in the TRD and is deliberately not duplicated.

## Diagrams

Diagram sources are committed, not only exports.

- Architecture and flow diagrams: **Mermaid** in a fenced block, or plain
  **SVG**. Both diff and review as text. `.gitattributes` deliberately does not
  route SVG through Git LFS for this reason.
- Mechanical drawings: commit the **native source and a rendered PDF or PNG**.
  Both are tracked by Git LFS.

A diagram that exists only as an exported image cannot be corrected by anyone
but its author, which is the same failure the hardware abstraction rule guards
against in code.
