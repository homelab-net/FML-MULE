===============================================================================
0. EXECUTIVE DISPOSITION
===============================================================================

This revision adds the BAOFENG DM-32UV as the selected external team voice-radio
interface and adds a MULE Radio-over-IP (RoIP) gateway capability.

The intent is:

    DM-32UV = independent local RF voice / PACE radio
    ATAK/EUD = map, data, collaboration
    MULE = resilient IP bearer, gateway, routing/security boundary

The DM-32UV remains capable of normal radio-to-radio operation when MULE,
Tailscale, WAN, ATAK, or the local mesh is unavailable.

When a MULE IP path is available, a dedicated DM-32UV gateway radio may bridge
local RF audio/PTT across:

    1. local conventional-Wi-Fi MULE IP;
    2. Wi-Fi HaLow MULE IP;
    3. Ethernet;
    4. approved USB/WAN uplink;
    5. Tailscale/WAN reachback.

LoRa/Meshtastic is NOT a baseline voice bearer.

The remote radio gateway does NOT need to use the same RF frequency as the
local gateway. Each gateway radio only needs to match its own local radio net.
The MULE transports decoded audio and PTT state as IP, not the RF waveform.

Example:

    Team A handhelds
        |
    RF Channel A
        |
    DM-32UV Gateway A
        |
    MULE-A
        |
    HaLow / Wi-Fi / Ethernet / Tailscale
        |
    MULE-B
        |
    DM-32UV Gateway B
        |
    RF Channel B
        |
    Team B handhelds

Channel A and Channel B may be different frequencies and may use different
local channel plans, provided each gateway is correctly configured for its
local users and the operating profile is lawful for the frequencies/services
being used.

The 4 GB / 32 GB CM4 remains the prototype compute candidate. RoIP audio/PTT
does not by itself justify returning to the 8 GB CM4. The full service-host
load remains subject to COMP-01 qualification.

===============================================================================
1. GOVERNING REQUIREMENTS PRESERVED
===============================================================================

The following existing FML principles remain controlling:

1. Local-first / WAN-independent.
   Loss of WAN shall not remove baseline local communications.

2. Voice PACE independence.
   MULE is an operational accelerator, not a replacement for independent
   mission-appropriate voice/manual PACE procedures.

3. Standard node architecture.
   All normal MULEs within an approved hardware block remain materially common
   and field-replaceable.

4. WAN overlay boundary.
   Tailscale terminates on MULE infrastructure. EUDs do not join the overlay
   merely to obtain MULE services.

5. External radio integration.
   The existing CONOPS already reserves Bluetooth, Wi-Fi, USB, audio, packet,
   and data integration boundaries for external VHF/UHF/HF radios.

6. Network reachability != authorization.
   A reachable Tailscale peer does not automatically receive permission to
   participate in a voice group or access another service/data domain.

7. Graceful degradation.
   Loss of the RoIP path returns the radio users to local RF operation.

8. Amateur-radio governance remains separate.
   Amateur operation requires an appropriate control operator and lawful
   content/configuration. Any feature that obscures message meaning must not be
   enabled on an amateur-radio profile where prohibited.

2. PROPOSED BASELINE CHANGES
===============================================================================

The lab reviewer should treat the following as proposed controlled changes.

FML-ADR-051 - SELECTED EXTERNAL VOICE RADIO
------------------------------------------------
BAOFENG DM-32UV is the selected initial standardized external team voice-radio
candidate for the current FML hardware block.

Rationale:
- group-standard radio;
- DMR Tier II + analog FM capability;
- VHF/UHF;
- GPS and DMR-based position reporting capability;
- USB-C charging;
- Kenwood-style two-pin programming/accessory family;
- commercially inexpensive and replaceable;
- independent radio operation preserves voice PACE.

Boundary:
- The radio is an external field radio, not a dependency for basic MULE
  networking/TAK functions.
- A different radio may replace it in a future hardware block if the controlled
  audio/PTT gateway interface is preserved and requalified.

FML-ADR-052 - SELECTED ROIP INTEGRATION PRINCIPLE
-------------------------------------------------
MULE extends external handheld-radio voice using audio/PTT-level Radio-over-IP,
rather than requiring native DMR protocol tunneling as the baseline.

Rationale:
- radio-agnostic;
- simpler than making native DMR/MMDVM routing mandatory;
- preserves existing user PTT behavior;
- can bridge different local RF frequencies/channel plans;
- allows later replacement of the radio while retaining the gateway interface;
- directly uses the MULE IP bearer architecture.

FML-ADR-053 - PROTOTYPE INTERFACE
---------------------------------
DigiRig Mobile revision 1.11-class USB audio/PTT interface with a Baofeng/Kenwood
K1 audio/PTT cable is the preferred first prototype interface.

This is a prototype implementation selection, not a permanent vendor lock.

The final production MULE may integrate equivalent CM108/USB-audio + PTT
electronics internally if testing demonstrates that integration reduces cost,
volume, and cable burden without reducing reliability.

3. NEW / REVISED REQUIREMENT CANDIDATES
===============================================================================

VOICE-MSN-001
The MULE subsystem SHALL support integration with the group-standard BAOFENG
DM-32UV external voice radio while preserving independent direct RF operation
when MULE services are unavailable.

VOICE-L1-001
A MULE SHALL be capable of accepting receive audio from a designated gateway
radio and providing transmit audio and PTT control to that gateway radio through
a controlled external-radio interface.

VOICE-L1-002
The baseline gateway SHALL operate at the audio/PTT level and SHALL NOT require
native DMR protocol termination to extend voice across the MULE IP fabric.

VOICE-L1-003
A MULE SHALL support forwarding authorized voice sessions across any approved IP
bearer that meets the voice service's latency/loss criteria.

Approved candidate IP bearers:
- conventional Wi-Fi MULE path;
- Wi-Fi HaLow;
- Ethernet;
- routed site/WAN;
- Tailscale overlay.

VOICE-L1-004
LoRa/Meshtastic SHALL NOT be considered a baseline RoIP voice bearer.

VOICE-L1-005
The local and remote gateway radios SHALL NOT be required to use the same RF
frequency. Each gateway SHALL use the approved local radio configuration for
its local operational domain.

VOICE-L1-006
Loss of IP voice connectivity SHALL NOT prevent local handheld-to-handheld RF
voice operation.

VOICE-L1-007
EUDs SHALL NOT be required to join Tailscale for RoIP operation.

VOICE-L1-008
The MULE SHALL remain the security/routing boundary for WAN/Tailscale voice
reachback.

VOICE-L1-009
Voice-group authorization SHALL be distinct from Tailscale/network
reachability.

VOICE-L1-010
The gateway SHALL include loop-prevention behavior so a voice session received
from another MULE is not retransmitted indefinitely through the MULE voice
fabric.

VOICE-L1-011
The gateway SHALL use half-duplex arbitration appropriate to PTT radio
operation. Only one active talker per configured voice group is required for
the initial baseline.

VOICE-L1-012
RoIP SHALL receive QoS preference over video, bulk synchronization, and large
file transfers, while not preventing critical TAK/CoT traffic from flowing.

VOICE-L1-013
The operator-radio path SHALL remain direct-to-radio for normal users.
Individual operator headsets/PTTs are not routed through the MULE.

VOICE-L1-014
The MULE SHALL support a dedicated gateway-radio role without creating a unique
leader-only MULE hardware variant.

VOICE-L1-015
Radio configuration/codeplug artifacts used for FML operation SHALL be version
controlled and associated with the applicable mission profile.

VOICE-L1-016
An amateur-radio mission profile SHALL prevent activation of radio settings or
gateway behavior that is prohibited under the applicable amateur operating
rules.

4. USER EXPERIENCE
===============================================================================

Normal team member:

    headset/PTT -> personal DM-32UV -> RF

No MULE interaction is required for normal local voice.

Gateway:

    local user's DM-32UV
        |
        | RF
        v
    dedicated gateway DM-32UV
        |
        | K1 speaker/mic audio + PTT
        v
    DigiRig / equivalent
        |
        | USB audio + serial RTS PTT
        v
    MULE

Remote voice:

    MULE-A -> MULE IP path -> MULE-B -> gateway radio -> remote local RF net

The normal user should not need to know whether a linked voice session crossed:
- one local MULE hop;
- multiple HaLow/Wi-Fi mesh hops;
- Ethernet;
- a mesh-connected WAN gateway;
- Tailscale.

The user's operational action remains:

    select assigned channel
    press PTT
    speak
    release PTT

6. SOFTWARE ARCHITECTURE REQUIRED
===============================================================================

The previous BOM treated "PTT/voice" largely as a future EUD/software function.
DM-32 integration changes that. A real gateway service and network-control path
are now required.

6.1 PROTOTYPE SOFTWARE COMPONENTS
---------------------------------

A. Linux USB audio
   - ALSA sees the DigiRig CM108 codec as a USB audio device.
   - Receive audio: gateway radio -> DigiRig -> ALSA capture.
   - Transmit audio: ALSA playback -> DigiRig -> gateway radio.

B. PTT control
   - DigiRig exposes an open-collector PTT switch.
   - PTT is controlled through the CP2102 serial interface using RTS.
   - The MULE gateway service asserts/deasserts PTT on authorized outbound
     voice sessions.

C. Audio codec
   Preferred prototype codec: Opus.

   Initial engineering profile:
   - mono;
   - voice-optimized;
   - approximately 12-24 kbps codec payload as a starting trade;
   - actual bitrate, frame size, FEC, and jitter buffer to be selected by test.

   This is an engineering starting point, not a locked TRD value.

D. Transport
   Preferred architecture:
   - direct MULE-to-MULE IP session;
   - local mesh route when local peer is reachable;
   - Tailscale route for remote peer where available/authorized;
   - no dependence on Internet-hosted voice server for local operation.

E. Control/signaling
   A thin MULE RoIP controller is required for:
   - voice-group identity;
   - origin node ID;
   - talker state;
   - PTT start/stop;
   - destination selection;
   - authorization;
   - session IDs;
   - loop prevention;
   - timeout/hang timers;
   - gateway state;
   - status/metrics.

   The service should be thin integration glue, not a new general-purpose
   telephony platform unless testing shows an existing mature project provides
   a better fit.

F. Service integration
   MULE Status Aggregator should report at minimum:
   - gateway radio interface present;
   - USB audio interface state;
   - PTT control state;
   - current voice group;
   - linked peer(s);
   - local-only / mesh-linked / WAN-linked state;
   - packet loss/jitter;
   - last voice session;
   - fault/loop lockout;
   - gateway enabled/disabled.

6.2 SOFTWARE IMPLEMENTATION TRADE
---------------------------------

TBR-VOICE-SW-01:

Compare at least:

1. thin MULE-native gateway:
   ALSA + Opus + direct authenticated IP transport + serial PTT control;

2. mature amateur/Radio-over-IP frameworks such as:
   - SvxLink-class architecture;
   - AllStar/Asterisk-class architecture;

3. other mature open-source RoIP components that:
   - run on current Debian stable ARM64;
   - support USB audio;
   - support external PTT;
   - work without public Internet;
   - can route over Tailscale/local mesh;
   - can be controlled by FML mission policy;
   - do not require a proprietary cloud.

Selection criteria:
- CPU/RAM;
- latency;
- ease of deployment;
- auditability;
- local-first behavior;
- security model;
- reliability;
- project health;
- ability to avoid unnecessary custom code.

No native DMR/MMDVM dependency is required for the baseline RoIP function.
MMDVM remains an optional future capability if native DMR metadata/talkgroup
integration proves valuable.

Selected external voice radio candidate:
BAOFENG DM-32UV.

Official current product information supports:

-----------------------------

Preferred first article:
DigiRig Mobile rev 1.11 or later.

Relevant current characteristics:
- USB audio codec based on CM108;
- CP2102 USB serial;
- independent open-collector PTT controlled by RTS;
- Linux support;
- one USB connection to host;

- 40-pin GPIO;

- RTC.

    CM4-IO-BASE-C USB Type-A
       |
    short USB-A -> USB-C data cable
       |
    DigiRig Mobile
       |
    Baofeng K1 audio/PTT cable
       |
    DM-32UV gateway radio

8.3 MECHANICAL TARGET
---------------------

ARTICLE 0:
DigiRig may remain external for rapid functional verification.

ARTICLE 1 / FIELD PROTOTYPE TARGET:
Mount DigiRig or equivalent inside the MULE enclosure if PACK-01 permits.

Preferred production human-factors outcome:
- no loose DigiRig box;
- one short controlled radio-interface connection to the dedicated gateway
  DM-32UV;
- protected/strain-relieved interface;
- MULE USB-C POWER/DATA/WAN port remains separate from the gateway-radio

If the K1 cable must pass through the enclosure, PACK-01 shall choose between:
A. sealed bulkhead connector + short replaceable K1 adapter; or
B. sealed captive pigtail with field-replaceable external adapter.

A sealed bulkhead is preferred for snag control and replacement, but it adds
a small custom harness task.

10. COST INTERPRETATION
===============================================================================

Do not interpret $762.94 as the eventual production cost.

The voice addition is intentionally using complete commercial prototype parts:
- $54.95 DigiRig;
- $34.45 cable set;
- $89.99 dedicated gateway radio.

The likely production cost-down path is:

1. Keep the DM-32UV as an external COTS radio.
2. Replace the external DigiRig enclosure with an internal equivalent USB-audio
   + PTT interface once the electrical interface is proven.
3. Replace the two-cable commercial set with one controlled short gateway cable.
4. Integrate the radio interface mechanically into the MULE enclosure.
5. Cost-reduce antennas/harnesses only after RF qualification.
6. Revisit high-rate Wi-Fi radio consolidation only after RF-03.

The voice-interface electronics themselves should eventually cost materially
less than the current $89.40 DigiRig + cable-set prototype combination, but no
production number shall be claimed until a board/harness quote exists.

11. PROCUREMENT / TEST GATES
===============================================================================

GATE VOICE-01 - DM-32 ELECTRICAL COMPATIBILITY
----------------------------------------------
Buy/borrow:
- 1 DM-32UV;
- 1 DigiRig Mobile 1.11+;
- 1 Baofeng HT DigiRig cable set.

Verify:
1. radio receives local RF;
2. clean receive audio appears in Linux ALSA;
3. MULE can play audio into radio microphone path;
4. RTS correctly keys PTT;
5. releasing RTS reliably unkeys;
6. no hot-plug damage;
7. no unintended PTT;
8. analog operation;
9. DMR operation;
10. acceptable RF feedback immunity;
11. acceptable audio levels without distortion.

PASS:
Stable bidirectional audio/PTT with repeatable levels.

FAIL:
Do not redesign the entire MULE. Replace only the external radio interface
cable/interface implementation.

GATE VOICE-02 - LOCAL ROIP
--------------------------
Two MULEs + two gateway radios.

Verify:

    DM-32 -> RF -> MULE-A -> local IP -> MULE-B -> RF -> DM-32

Use both:
- conventional Wi-Fi;
- HaLow where available.

Measure:
- one-way latency;
- jitter;
- packet loss;
- audio intelligibility;
- PTT acquisition delay;
- PTT release/tail behavior;
- CPU/RAM;
- link recovery.

GATE VOICE-03 - DIFFERENT RF CHANNELS
-------------------------------------
Configure Gateway A and Gateway B for different legal/authorized local channel
configurations.

Verify audio/PTT transit over IP works without RF-frequency equality.

This explicitly proves the architecture is an audio/PTT gateway, not an RF
repeater requiring a common frequency.

GATE VOICE-04 - TAILSCALE
-------------------------
Verify:

    DM-32 -> MULE-A -> Tailscale -> MULE-B -> DM-32

Then verify:

    DM-32 -> MULE-A -> local mesh -> MULE-C WAN gateway

12. TRAFFIC / QOS POLICY DELTA
===============================================================================

Proposed traffic classes:

Highest preservation:
- critical network control;
- required TAK/CoT/PLI;
- active PTT/RoIP voice signaling and audio.

Next:
- GeoChat / operational messaging;
- TAK service sessions;
- routine application traffic.

Lower:
- file transfer;
- synchronization;
- video;
- background analytics.

Voice characteristics:
- latency-sensitive;
- low bandwidth;
- loss tolerant within limits;
- must preempt/deprioritize bulk/video rather than allowing large flows to
  make PTT unintelligible.

Initial engineering objective:
- do not lock a final latency requirement until VOICE-02/04 testing;
- use a small jitter buffer;
- optimize for intelligibility and PTT responsiveness, not broadcast-quality
  audio.

===============================================================================
13. SECURITY / AUTHORIZATION DELTA
===============================================================================

Tailscale authentication alone is insufficient.

Voice authorization shall include:
- mission identity;
- gateway identity;
- voice-group permission;
- destination scope.

Example groups:
- TEAM-LOCAL
- TL-NET
- COMMAND
- EVENT / INCIDENT
- TEST

The exact group names are operational configuration, not hard-coded product
requirements.

A remote MULE that is reachable by IP must not automatically be able to:
- key another team's radio;
- join command voice;
- forward audio into another organizational scope.

Minimum control concepts:
- authenticated gateway peers;
- allowlisted voice groups;
- short-lived mission configuration;
- session IDs;
- origin node ID;
- replay/loop protection;
- maximum transmit timeout;
- emergency administrative disable.

The radio itself remains governed by the applicable RF operating authority and
mission profile.

===============================================================================
14. REGULATORY / RADIO CONFIGURATION NOTES
===============================================================================

The DM-32UV is capable of both analog and DMR operation.

FML should NOT hard-code actual transmit frequencies into the engineering BOM.

Channel/frequency/talkgroup configuration belongs in the approved mission radio
plan and must match applicable authorization.

For amateur-radio use:
- appropriately licensed/control-operator requirements remain applicable;
- FML must not rely on prohibited message-obscuring/encryption features;
- gateway behavior must follow applicable station identification, forwarding,
  control, and content requirements.

For other appropriately authorized services:
- configuration must match the applicable license/rules/authorization.

The existence of an FCC-certified radio does not itself authorize use on an
arbitrary frequency.
